## 2. Interface boundaries
* Shared constants (column lists, warn codes, modes, tick, IST offset 19800) are duplicated in `python/pe/schema.py`, `cpp/include/pe/types.hpp` and `docs/SCHEMAS.md`; consistency is enforced by parity tests only. `forensics.py` has a further private `IST = 19800`.
* Serialization: tab separated, `\n`, integers (paise, units, epoch seconds), AVG decimals `%.6f` (Python f-string and C `snprintf` agree on all tested values), sorted ids (Python code-point order = C++ byte order for the ASCII ids in use), `source_row_id` final tie-break.
* Ids (VERIFIED on 41,421 fills): fill_id = `F%06d` of raw row; OA/CP = `OA:`/`CP:` + fill_id; episode = `instrument#n`; LE = `LE:episode:seq`; CA = `CA:conv:fill:n`; batch = `INF:CLOSING_BATCH@token:und:expiry:session:nnn`; item = `WBI:level:role:parent:instrument`; link = `WB:method:level:item->item`. All unique (including all 42,777/65,228/12,096 link ids), no parent id contains `:`/`|`/tab; lineage files byte-identical when the input is shuffled (3 seeds) or reversed. LE-id uniqueness is not checked by `LineageSet.check` (E02 shows).
* Python vs C++ reader semantics differ for non-canonical tokens (E-D05). Python has no int64 overflow guard (E-D06).
* `fill_id` zero-pad width 6 is safe for 41,421 rows (max row 41,420); a ledger over 10^6 rows still yields unique ids.
